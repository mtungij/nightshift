# Nightshift development

Nightshift preserves the dark-and-gold workspace and POS UI while using authenticated Laravel 13 endpoints, Livewire 3.8, and database-backed transaction services. Business records are never persisted to browser storage. An unsaved POS cart lives only in page memory.

## Local setup

Requirements: PHP 8.3+ with PDO SQLite, PDO MySQL and BCMath; Composer; Node.js and npm. SQLite is the current development connection. MySQL 8.4 is the target production database, pending a dedicated account and a complete MySQL validation run.

```bash
composer install
npm ci
cp .env.example .env
php artisan key:generate
php artisan migrate
php artisan db:seed --class=NightshiftDemoSeeder
npm run build
php artisan serve
```

Do not overwrite an existing `.env`. Keep `DB_CONNECTION=sqlite` for current development. The demo seeder is repeatable, uses its own company, and refuses to run in production.

Nightshift login uses only a unique username and an exactly four-digit PIN, for every role. Usernames are shown in **Wafanyakazi**. The username migration preserves all users, role/company assignments, passwords and existing PIN hashes; it assigns generated usernames in the form `name-userid`. Missing PINs remain unconfigured rather than receiving a shared default. Never seed demo users on a production database.

Provision the first owner's PIN from a terminal, using that owner's actual username (the first seeded owner is usually `alex-morgan-1`):

```bash
php artisan nightshift:set-login-pin alex-morgan-1
```

The command prompts twice with hidden input. Do not put a PIN in command arguments. After signing in, Owner/Admin can set or reset every role's PIN from **Wafanyakazi**, including their own. The same PIN is used for login, Quick Lock and eligible waiter POS confirmation. New staff and business owners supply a username and PIN; their backend passwords are generated securely.

Login usernames are globally unique so no company selector is needed. `/companies/{company_id}/login` binds a login to that company and rejects other companies' users. Email verification is not required. Five failed PIN checks lock the account for 15 minutes across login, Quick Lock and POS; login also has username/IP and IP-wide rate limits. Existing two-factor authentication remains active for accounts that configured it.

The seed creates real products, selling units, independent stock at four locations, posted goods receipts, waiter and cashier shifts, invoices and a partial payment. Seed quantities and balances are generated by the same services used by the application.

## Staff visibility

Operational reads use `StaffVisibility` plus order/shift policies, in addition to company and branch scopes. Waiters receive only their own orders, account ledger, payments and shifts; their shift view has no cashier reconciliation fields. Cashiers receive their own shifts, reconciliation and payment activity. Their settlement view contains eligible waiter identities, unpaid invoices and balances at their open cashier shift's counter, falling back to their latest cashier shift's counter after closing. A cashier without a shift receives no staff operations. Minimal permitted counter metadata remains available to open the next shift; selecting a new counter updates the operational scope immediately.

`view-staff-operations` explicitly permits broader staff operations. Owner/Admin has company-wide access. Manager and Supervisor have branch-scoped access by default; `all-branches` is a separate explicit grant for wider access within the same company. Generic report or staff-management permission alone does not grant private operational records. Backend checks also cover report exports, receipts, issue tickets, notifications and command IDs.

Visibility queries do not replace accounting queries: the lifetime waiter ledger still determines settlement and shift-close invariants. Branch/counter balances shown to staff use scoped read queries. The migration preserves financial history and staff assignments, tags new notifications with staff/counter ownership, and removes Manager's previously inherited default `all-branches` grant. Old notifications without ownership tags remain visible only to authorized management within branch scope.

## Transaction rules

- Every request resolves the authenticated company. Tenant Eloquent models fail closed without that context. Scoped records also enforce permitted branch assignments. Composite tenant foreign keys reject references to a different company.
- Gates use database roles and permissions. User requests cannot choose a company, change their role, or become a super administrator. Role preview has been removed.
- Decimal strings and BCMath perform monetary and quantity arithmetic. Products have no inventory quantity column; `stocks` holds each product/location balance. Document items retain the original price, conversion, cost and product name.
- Commands execute inside retryable database transactions. The company row is the first mutation lock, followed by order, shift, sequence and stock row locks. This deliberately serializes writes within a company and provides a consistent lock order. MySQL/InnoDB enforces these locks. SQLite serializes writes; conflicting transactions fail or retry rather than partially posting.
- Creating or submitting an order never changes stock. Issue requires an open cashier shift at the order counter and an open waiter shift. All item deductions, source movements, issue metadata and waiter liability post together.
- All mutation requests require a UUID idempotency key. Repeating the same command and payload returns its original result. Reusing a key for different data is rejected. Issue, transfer and approval services also guard against duplicate posting independently.
- Cash, mobile money, card and bank payments create immutable payment allocations and waiter credits. Credit records a promise to pay and never pretends to settle debt or cash. Subsequent received payments settle the balance. Credit promises are not payment allocations.
- Waiter ledger, payments, allocations, stock movements, receipt items, return items and audit records cannot be edited or deleted through their models. MySQL migrations additionally install immutable-history triggers and nonnegative-stock/check constraints. Application services enforce these invariants on SQLite without SQLite-specific schema or query syntax.
- Item returns cannot exceed issued quantity minus previous returns. Discount shares and the final return remainder are preserved so returning every item reconciles exactly. Returns of paid monetary value require an approved void/refund workflow. Zero-value returnable items can still be restored without a refund.
- Void approval requires confirmation of recovered goods. It restores only unreturned stock, posts a liability reversal, records refund payments and their ledger reversals when necessary, and retains all original documents. Refunds require the approver's open cashier shift at the counter. Rejection restores the previous state.
- Transfers are drafted, sent into `IN_TRANSIT`, and received separately. Sending debits only the source; receipt credits only the destination. Transfers currently require both locations to belong to the same branch.
- Adjustments always require a manager decision. Rejected requests never touch inventory. Waiter closure checks lifetime outstanding debt, and a manager override requires a recorded reason without erasing the balance.
- Expected cashier cash equals opening cash plus signed cash payments/refunds on that cashier shift. A nonzero difference requires an explanation.

## HTTP integration

The workspace is `/dashboard`, hosted by a Livewire component. The existing renderer calls session-authenticated, CSRF-protected endpoints under `/api/nightshift`. API responses use the same company and branch scopes as the service layer.

- `GET /bootstrap`: permission-filtered workspace data and actual dashboard aggregates. Catalogs and document feeds are bounded; reports provide date-filtered database queries.
- `POST /commands/{command}`: validated command with `idempotency_key` plus its payload. Services authorize every sensitive operation; no submitted prices, totals, tenant IDs or balances are trusted.
- `GET /reports/{name}`: database-backed reports with permitted company/branch/date/product/category/location/employee filters, 100-row pages, and `has_more`.
- `GET /reports/{name}/export`: streamed CSV of all matching pages.
- `GET /receipts/{order_id}`: protected receipt with original item snapshots, payments and balance. Print CSS targets 80mm thermal paper.

The workspace refreshes every 30 seconds when no input, modal or command is active. Request errors are visible and never presented as successful local changes.

```bash
vendor/bin/pint --test

```

Feature coverage includes existing authentication/settings tests and ERP isolation, stock, issue, idempotency, ledger, split/partial payment, credit, returns, void/refund, goods receipt, transfer, approval, shift, dashboard/report and receipt cases. Double submission tests are deterministic; actual simultaneous MySQL cashier requests and MySQL trigger behavior must also be validated on MySQL before release.

## MySQL cutover

Do not change machine-level MySQL users or authentication. Provision a dedicated database/account separately and set `DB_CONNECTION=mysql`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, and `DB_PASSWORD` in the deployment environment. Use InnoDB and the strict configuration already in `config/database.php`. Run migrations and the complete test suite against an isolated MySQL 8.4 test database before production. The default PHPUnit configuration intentionally targets disposable in-memory SQLite; a MySQL validation run must override those test connection settings.

This repository is not yet validated for a production deployment on MySQL. Complete that cutover validation, real concurrency tests, backup/restore verification and deployment configuration before accepting live business transactions.

## Per-company WhatsApp reports and alerts

WhatsApp is off by default. Owners use **Settings → WhatsApp** to link a company device, add normalized Tanzanian recipients, choose recipient branch scopes, and enable reports or alerts. Managers have branch-scoped recipient, test, report, and log access by default; global integration settings require `whatsapp.manage_settings`. Cashiers, waiters, and store keepers have no WhatsApp settings permissions by default.

Shared provider credentials belong only in `.env`: `GOWA_URL`, `GOWA_USERNAME`, `GOWA_PASSWORD`, and `GOWA_WEBHOOK_SECRET`. The device ID is stored once per company, never as a global device environment variable. Browser requests cannot choose arbitrary device IDs or enumerate server devices. New slots have server-generated company-specific IDs. An operator can assign a verified existing provider slot with `php artisan whatsapp:assign-device COMPANY_ID DEVICE_ID`; slots cannot be shared across companies.

The provider adapter follows the [Gowa OpenAPI endpoint reference](https://github.com/aldinokemal/go-whatsapp-web-multidevice/blob/main/docs/openapi.yaml) and the supplied integration guide. Confirm the deployed server’s exact schema for device creation, QR/pairing responses, and file sending before enabling real use. Only HTTPS is accepted; TLS verification stays enabled. Credentials, provider response bodies, and authentication headers are never returned to the browser or copied into delivery errors. QR images are fetched through a restricted backend proxy.

Reports include consolidated or per-branch daily owner summaries and committed cashier shift summaries. Seven optional alert types are supported: waiter outstanding, cash shortage, low stock, approved voids, breakage, complimentary items, and large sales. Alert thresholds and cooldowns are configurable. Stock alerts reset after replenishment and may retrigger on a configured further drop. Reporting reuses the existing dashboard, report, and ledger accounting; monetary arithmetic uses the existing decimal helper. Company timezone determines daily report dates and due times. Daily reports are snapshots generated at the configured time, not a declaration that the business day is closed.

Operational sends always use the asynchronous database `whatsapp` queue, even if the application’s default queue is synchronous. The committed audit log supplies operational events; failed queue pushes are recovered by the scheduler. A single normal Laravel scheduler entry runs company planning every minute and queues device checks at most once per 15 minutes per company.

For a future deployment, configure the standard Laravel scheduler cron and supervise this worker:

```bash
php artisan queue:work database --queue=whatsapp --tries=3 --timeout=60
php artisan schedule:run
```

Delivery logs persist company, recipient, branch scope, device, reporting period/reference, attempts, provider message ID, status, and sanitized failure details. Successful deliveries and daily/shift references are deduplicated. Safe failures retry with 10/60/300-second backoff. An interrupted send, timeout, or accepted response without a message ID is marked for verification and is not automatically resent: the documented provider send endpoint has no client idempotency token, so an unknown delivery cannot be retried with an exactly-once guarantee.

Automated tests use HTTP fakes and never send real WhatsApp messages. The dedicated inventory/WhatsApp browser fixture scripts refuse to run against any database except `storage/framework/testing/nightshift-ux-browser.sqlite` with `APP_ENV=testing`; their Gowa requests are also faked. No inbound WhatsApp command automation or production deployment is included.
